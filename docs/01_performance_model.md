## 1. Roofline：一张图定方向

任何 kernel 的性能都被两条天花板同时压住：

```
                                峰值算力（本机 ~13 TFLOP/s）
                                      │
  性能                               │
   │                    ┌────────────┘
   │                   ╱
   │                  ╱   ← 转折点 = machine balance ≈ 54 FLOP/Byte
   │                 ╱
   │                ╱        斜率 = 峰值带宽 256 GB/s
   │               ╱
   │              ╱
   │             ╱
   └────────────┴───────────────────────────────────→ 算术强度
   0.01      0.1      1       10      54     1000     (FLOP/Byte)
              ↑        ↑
        add 0.083   relu 0.125
```

**转折点左边 = memory-bound，右边 = compute-bound。** 本仓库目前所有算子都在最左边
（`add` 0.083、`relu` 0.125、`hello` 0.25），差了转折点几百倍。

**所以对它们来说，"优化"只有一个意思：打满那条 256 GB/s 的斜线。**
减少计算量、换更快的指令、用更聪明的算法——**全是无效动作**。

> 什么会落在转折点右边？GEMM。`C = A @ B` 在 512×512 时算术强度约
> `2·512³ / (3·512²·4)` ≈ 85 FLOP/Byte，已经过线。这就是为什么第 8 章
> 才是比赛核心——**它需要的是完全不同的一套优化手段**。

## 2. 理论下限：把"斜线"变成一个具体数字

```
理论最短耗时 = 搬运字节数 / 峰值带宽
```

| 算子 | 搬运量（N = 2²⁴） | 理论最短 | 实测最好 | 实测/理论 |
|---|---|---|---|---|
| `add` | 201.3 MB | 786.3 µs | 839.6 µs | **1.07×** |
| `relu` | 134.2 MB | 524.2 µs | 583.1 µs | 1.11× |
| `sigmoid` | 134.2 MB | 524.2 µs | 588.5 µs | 1.12× |
| `bandwidth_probe` | 134.2 MB | 524.2 µs | 564.2 µs | 1.08× |

**实测普遍落在理论下限的 1.07~1.12 倍**，也就是带宽利用率 89~94%。

这个区间是**正常的**：DRAM 有刷新、行切换、读写转向等固有开销，流式访问很少能超过
93% 左右。所以"到 85% 就停手"这条经验规则其实还偏保守 —— **到 93% 就该停手了**。

> 什么时候该警惕？如果你算出来的理论下限是 786 µs，实测 2000 µs（2.5×），
> 那说明有真实的结构性浪费，值得挖。如果实测 850 µs，**去找别的算子优化吧**。

## 3. Occupancy：被误解最多的一个概念

### 它是什么

`occupancy = 每 SM 实际驻留的 warp 数 / 硬件允许的最大 warp 数`。

同一个 SM 上同时驻留的 warp 越多，一个 warp 卡在访存上时，越有别的 warp 可以顶上去
——这就是"用并发掩盖延迟"。

### 它**不是**什么

**occupancy 不是越高越好。** 它是一个**手段**，不是**目标**。判断标准永远是带宽到没到。

### 本仓库的实测证据

**证据一：第 1 章的受控实验**（同一份 kernel，只改动态 smem 当 occupancy 旋钮）

| 动态 smem | 理论 occupancy | GB/s |
|---|---|---|
| 0 KB | ~100% | 226.3 |
| 24 KB | ~67% | 225.6 |
| 32 KB | ~50% | 226.0 |
| 48 KB | **~33%** | **237.9** |

**占用率掉到 1/3，带宽不但没掉，反而高了 5%。** 这个 5% 目前还是未解之谜
（见 [第 1 章 README](../kernels/01_execution/README.md)），但它已经足够说明一件事：
**occupancy 和带宽之间不是简单的正相关。**

**证据二：第 2 章的寄存器分析**

五个变体的寄存器用量从 12 涨到 34，看起来"寄存器多了 → occupancy 会掉"，对吗？

| 变体 | 寄存器 | 实测 %峰值 |
|---|---|---|
| `v1_naive` | 12 | 93.7% |
| `v2_unroll4` | 25 | 92.3% |
| `v3_grid_stride` | 34 | 92.2% |
| `v4_vectorized` | 18 | 91.5% |

**不对。** sm_89 每 SM 有 65536 个寄存器、最多 1536 线程；block = 256 时是**线程数**
先绑死在 6 个 block。6 个 block 在 34 个寄存器下也只需要 `6×256×34 = 52224 < 65536`。

**所以五个变体全都是 100% occupancy，寄存器从 12 涨到 34 根本没碰到天花板。**

而且 `v4` 寄存器**更少**（18）却也**更慢** —— "寄存器 → occupancy → 带宽"这条链
在这里完全不成立。

> **这条教训的通用形式**：拿到一个性能问题，先确认瓶颈**在哪一层**，再谈优化。
> 寄存器多不一定占用率低；占用率低不一定带宽低；带宽低不一定是因为没合并访存。
> 本仓库两次"想当然"都被数据推翻了。

## 4. Latency hiding：为什么线程少也能打满带宽

```
需要的在飞请求数 = 访存延迟 × 带宽
```

本机：延迟约 400~600 个 SM 周期，带宽 256 GB/s。两者相乘意味着**同时在飞的请求
必须有几千上万个**。这个数从哪来？

### 来源一：线程数（occupancy）

每个线程一个在飞请求 → 你需要大量线程。

### 来源二：每线程的 ILP

每个线程一口气发 4 个互不依赖的 load → 线程数可以少 4 倍。
第 2 章的 `v2_unroll4` 就是这条路：**先把 4 个 x 和 4 个 y 全部 load 进来，
再统一计算、统一 store**。`SASS` 确认快路径是 8 个连续 `LDG` 后接 4 个 `STG`。

> 为什么必须"先全 load 再统一 store"：如果把 `if (i < n)` 塞进循环里，编译器
> 无法确定 4 个 load 都会执行，只能一个一个来 —— ILP 就没了。

### 来源三：编译器白送的

第 2 章的 `v3_grid_stride` 写的是一个朴素的循环，但 `SASS` 显示
**nvcc 自动把它展开了 4 路**。所以它也白拿了 ILP，代价是寄存器升到 34。

**这三条路是可以互相替代的**——这正是"occupancy 低不等于性能差"的机制解释。

## 5. 决策流程：拿到一个算子该按什么顺序想

```
1. 算算术强度 → 和 machine balance 比
   ├─ 远低于 → memory-bound：目标 = 打满带宽
   └─ 高于   → compute-bound：目标 = 减少运算 / 用更快的指令
        ↓
2. 算理论下限 = 搬运量 / 峰值带宽
   （这个数字后面每一步都要拿来做判据）
        ↓
3. 实测，看占峰值百分比
   ├─ ≥ 90%  → 停手，写清为什么到不了 100%，去做别的
   └─ < 60%  → 有结构性问题，继续
        ↓
4. 定位瓶颈层
   ├─ 访存模式问题？ → 看合并 / 向量化 / 对齐
   ├─ 并发度问题？   → 看每线程元素数 / ILP / occupancy
   └─ 都不是？       → ncu 看 stall 原因
        ↓
5. 改一处、实测、记录"相比上一级"
   （一次只改一个变量，否则归因不了）
```

第 4 步的具体查法见 [operator_performance_analysis.md](operator_performance_analysis.md) 的
"症状 → 病因"对照表。

## 6. 两条容易被忽略的纪律

### 6.1 先写预测

第 1 章的 occupancy 实验，我在写代码前写下了预期。实测**错了一半**——
而那一半的错比全对更有价值，因为它指向了一个没被理解的现象。

**不写预测，你只会看到"四档都差不多"然后翻页过去。**

### 6.2 一次只改一个变量

第 2 章的 `v4_vectorized` 刻意**不加** grid-stride：`v4 = v1 + float4`，
只改"访存宽度"这一个变量。如果同时加了 grid-stride，那么"v1 → v4 的差距"
就无法归因了。

同理，`v0_uncoalesced` 与 `v1_naive` **只差索引公式那一行**，连寄存器数都完全一样
（都是 12）——这样 4.39× 的差距就**只能**归因于访存模式。

> 这条纪律在第 2 章被证明极其重要：正因为每级只改一个变量，我们才能确信
> "v2/v3/v4 没有提升"是真实的，而不是被别的因素掩盖了。
