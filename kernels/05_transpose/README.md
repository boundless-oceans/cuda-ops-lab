# 05 Transpose（转置）

> 这一章的阶梯**三次被打脸，三次都值钱**：
>
> 1. 我以为"跨步读比跨步写更惨"——**实测反过来**，跨步写慢 1.81 倍。
> 2. 我以为 padding 消 bank conflict 能值 5~25%——实测 **5.1%**，只在下沿。
> 3. 我以为宽瓦片能改善 DRAM 突发局部性——实测 **0.4%，等于没有**。
>
> 而唯一没被打脸的是"用共享内存让两边都合并"那一级：**1.28×，全章最大的一步。**
>
> 顺带一个结果：**我们的 572.8 µs 比 `torch` 的 1069.5 µs 快 1.87 倍** ——
> `torch.transpose(...).contiguous()` 在这台机器上只有 49% 峰值。

---

## 1. 问题定义

| 算子 | 数学定义 | 输入 → 输出 | `bytes` | `flops` |
|---|---|---|---|---|
| `transpose` | `out[c][r] = in[r][c]` | `float32[M][N]` → `float32[N][M]` | 8MN | **0** |

约束：`float32`；**只支持 2 维输入**（转置是二维算子，"展平一个 3 维张量再转置"
没有明确语义）；任意 `M, N ≥ 0`；参考实现在 `float64` 上。

三处和前面几章不同的地方，都是刻意的：

| 项 | 做法 | 理由 |
|---|---|---|
| 形状 | **二维** `(rows, cols)` | 前面五章全是 1 维。于是 `out_shape` 字段第一次真的用上：输出是 `(cols, rows)` |
| 容差 | **精确相等**（`rtol = atol = 0`） | 转置是**纯置换**，一个算术运算都没有 —— 任何"搬错一个元素"都该被抓到 |
| `flops` | **0** | 本章不做任何算术，算术强度恒为 0。这是"纯数据搬运"的极端 |

`bytes = 8MN`（读 4MN + 写 4MN），与第 2、4 章同一个访存形态 ——
所以本章的成绩可以直接放进"访存形态 vs %峰值"那张横向对比表（见 §3）。

## 2. 先算两笔账（★ 写代码之前）

### 第一笔：跨步的那一边 —— 转置独有的麻烦

搬运量和第 2 章一样，但**总有一边是跨步的**：要么读跨步、要么写跨步。
我当时的推理是：

> 读的数据要立刻拿到才能算，延迟藏不住 → 跨步读更惨；
> 写只要进了回写缓冲就算完事 → 跨步写便宜些。

**这个推理错了，方向完全反。** 实测（见 §3）：

```
v0_naive   （读合并、写跨步）  1392.6 µs   37.6%
v1_swapped （读跨步、写合并）   769.0 µs   68.2%   ← 快 1.81 倍
```

修正后的机制（**待 ncu 验证，见 §5**）：

* **跨步写**每次只写一个 32 B sector 里的 4 B → **部分写**。sector 的其余字节由别的
  warp 在别的时刻写，L2 不一定留得住 → 落到 DRAM 就是一次 **read-modify-write**，
  **凭空多出一份读流量**。
* **跨步读**虽然把一个 warp 的请求从 4 个 sector 放大到 32 个，但那些 sector 里的
  其它 7 个 float 恰好被**同一个 block 的其它线程**用到 → 被 L2 接住，
  **显存字节数不变**。

也就是说：**跨步写的代价是"多搬了字节"，跨步读的代价只是"多发了几次请求"。**
前者伤带宽，后者伤事务率 —— 而在这台机器上带宽才是瓶颈。

### 第二笔：smem 比 DRAM 快多少 —— 决定 padding 值不值钱

```
smem:  32 bank/SM × 24 SM = 768 次 bank 访问/cycle（× 实测 SM 时钟 2430 MHz）
DRAM:  256 GB/s ÷ 8 B/元素 = 3.2e10 元素/s
```

| 状态 | 每元素 smem 访问 | smem 能喂多少元素/s | 相当于 DRAM 的 |
|---|---|---|---|
| 无冲突 | 写 1 + 读 1 = 2 | 9.3e11 | **29 倍** |
| 32 路冲突 | 写 1 + 读 32 = 33 | 5.7e10 | **1.8 倍** |

所以预测不是"慢 2~4 倍"，而是：

> **v3_padded 比 v2_smem_tiled 快 5~25%** —— 冲突会露出来一点，但远不到教科书的量级。

实测 **5.1%**（预测的下沿，见 §3）。**冲突是真的，但它几乎被掩盖了** ——
因为即使被 32 路冲突打回原形，共享内存仍然比显存快 1.8 倍。

**这一章和第 3 章的对照是刻意的**：第 3 章的 padding 是**真·空操作**（顺序寻址本来就
没有冲突），这里的冲突是**真实存在**的。两章合起来才能说清"经典优化什么时候有用"。

### ★ 一个新踩的坑：`float4` 的对齐条件比"尾部"更宽

v4/v5 的 float4 快路径要求 16 字节对齐。我写了"尾部不足 4 个元素走标量"，却漏了
**"行起点本身就不对齐"**：

```cuda
in + in_row * cols + in_col      // in_col 是 4 的倍数，但 in_row*cols 只有在
                                 // cols % 4 == 0 时才对齐
```

列数不是 4 的倍数时，从**第二行起**整个错位 → `CUDA error: misaligned address`。
更坑的是：**一次 misaligned 访问会污染 CUDA 上下文**，之后所有 API 调用都报同一个错，
于是测试里连**没有 float4 的 v0** 也"失败"了（10 个用例全红，看起来像全盘崩溃）。

修法：把对齐也算进快路径条件（`cols % 4 == 0 && rows % 4 == 0`，加上指针本身 16 字节对齐），
由 host 侧算好传进 kernel。**基准形状 4096×4096 两个方向都是 4 的倍数，所以成绩表一直是有效的**
—— 只有非 4 倍数的形状（测试里的 `(31,33)`、`(255,257)`）会踩到。

设备：RTX 4060 Laptop（sm_89，24 SM），4096×4096，理论下限 524.2 µs。

```

测时显存时钟 8001 / 8001 MHz（满速）
计时：3 轮交错（轮间起始变体错开），每轮 warmup 20 + 40 次独立 record/sync
```

| `v1_swapped` | 反面教材：**读跨步**、写合并（与 v0 只差交换 `(r,c)`） | 769.0 | 14.1 | 174.5 | 68.2% | **1.81×** |

**最快变体 `v3_padded`：572.8 µs = 理论下限的 1.09×、91.5% 峰值，
比 torch 快 1.87 倍。**

### 这张表是"三段爬升 + 一条平线"，前五章里的第一次

| 台阶 | 值多少 | 为什么 |
|---|---|---|
| v0 → v1 | 1.81× | **跨步写在读、还是在写**（见 §2 第一笔账） |
| v1 → v2 | 1.28× | 用 smem 让**两边都合并** |
| v2 → v3 | 1.05× | 消掉 32 路 bank conflict（**真的，但只有 5%**） |
| v3 → v4 → v5 | 1.00× / 1.00× | 向量化与瓦片宽度**都没有用** |

### 预测 vs 实测

| 预测 | 实测 | |
|---|---|---|
| v0 差，但不是 32 倍 | 比最优慢 **2.43 倍** | ✅ |
| **v1 比 v0 更差** | **v1 比 v0 快 1.81 倍** | ❌ **方向完全反了** |
| v2 相对 v1 一大步 | 1.28× | ✅ |
| v3 比 v2 快 5~25% | **5.1%** | ⚠️ 方向对，幅度在下沿 |
| v4 ≈ v3 或更慢 | 1.00×（差 0.02%） | ✅ |
| v5 好 5~15%，很可能测不出来 | **0.4% 更慢**（噪声内） | ✅ 就是测不出来 |

**v2 → v3 那 5.1% 是可信的**：29.2 µs 的差距，而两个变体的轮间极差只有 1.2 / 1.8 µs
—— **差距是噪声的 16 倍以上**。它和第 3 章"padding 完全没用"形成了完整对照。

| 访存形态 | 最好成绩 | %峰值 |
|---|---|---|

## 4. 每级实现要点

### `v0_naive` / `v1_swapped` —— 两个反面教材，只差两行

```cuda
// v0：读合并、写跨步
const int r = blockIdx.y * kNaiveBlock + threadIdx.y;
const int c = blockIdx.x * kNaiveBlock + threadIdx.x;
out[c * rows + r] = in[r * cols + c];

// v1：交换 (r,c) 的取法（grid 形状跟着换），于是读跨步、写合并
```

**这一对是本章最值钱的对照**：同样的一个 kernel、同样的搬运量，
只因为"跨步落在读上还是落在写上"，差了 **1.81 倍**。
而教科书的直觉（读更怕跨步）在这台机器上是**反的**（机制见 §2）。

### `v2_smem_tiled` / `v3_padded` —— 与 v2 只差一个模板实参

```cuda
template <int kStride>   // v2 = 32，v3 = 33
__global__ void transpose_tiled_kernel(...) {
  __shared__ float tile[kTileRows][kStride];
  // ① 载入：tile[ty+j][tx] = in[...]     相邻 tx 相邻地址 → 读合并
  ...
  // ③ 写回：out[(out_row+j)*rows + out_col] = tile[tx][ty+j]
  //         ★ kStride=32 时地址是 tx*32+(ty+j) → bank 全等于 (ty+j) → 32 路冲突
  //           kStride=33 时地址是 tx*33+(ty+j) → bank = (tx+ty+j)%32 → 两两不同
}
```

写回阶段的两组下标是**交叉**的（输出行 = 输入列，输出列 = 输入行），
两个边界条件也随之交叉 —— 所以在部分瓦片（M 或 N 不是 32 的倍数）上，
**没被写入的 smem 格子也不会被读出来**。这是这一级最容易写错、也最容易测漏的地方。

### `v4_vectorized` / `v5_wide_tile` —— 两级都只差一个模板实参

```
v4 = transpose_vec_kernel<32, 33>
v5 = transpose_vec_kernel<64, 65>
```

结构（`transpose_vec.cuh`）：block = (8, 32)，每个线程一次搬一个 **float4**；
载入读 4 个连续**列**，写回写 4 个连续**输出列**（= 4 个连续输入行）。
**共享内存仍然用标量读写**，所以行宽 +1 就足以消冲突。

> **为什么不用 swizzle**：如果共享内存也要 float4 读写，行宽就必须是 4 的倍数，
> 而 4 的倍数与 32 不互质（`+4` 时 bank 偏移变成 `4·行`，8 行绕回原处）→
> padding 这一招失效，真实实现（CUTLASS 等）此时改用 **XOR swizzle**。
> 本章不做，因为它会把"瓦片宽度"这个变量污染掉 —— 但这条边界值得记住。

**两者的实测都是 1.00×**：向量化省的是**指令数**，瓦片加宽改的是**突发长度**，
而这两样在这台机器上都不是瓶颈（第 2、4 章已经各证过一次）。

## 5. ncu 观察

### 最值得做的那一个：v0 vs v1 —— **验证"跨步写要付 RMW"这个事后解释**

```bash
ncu -k "regex:transpose_v0_kernel" --launch-count 1 --set full ./build/native/main_05_transpose
ncu -k "regex:transpose_v1_kernel" --launch-count 1 --set full ./build/native/main_05_transpose
```

| 指标 | 预测 |
|---|---|
| **`dram__bytes_read.sum`** | **v0 明显高于 v1**（部分 sector 写触发 read-modify-write，凭空多出一份读流量）。理想值都应是 4MN = 67.1 MB |
| **`dram__bytes_write.sum`** | 两者应接近（都是 4MN = 67.1 MB） |
| `lts__t_sectors.sum` | v1 更高（跨步读把请求从 4 个 sector 放大到 32 个） |
| `gpu__time_duration.sum` | v0 是 v1 的 **1.81 倍** |

**这是本章最值得验证的一条**：如果 v0 的 `dram__bytes_read` 并没有比 v1 高，
那"部分写 → RMW"这个解释就错了，得另找机制（那种情况下我会先怀疑
"v0 的写事务数把 L2 打爆了"）。

### 再看：padding 那 5.1% 到底出在哪

```bash
ncu -k "regex:transpose_tiled_kernel" --launch-count 1 --set full ./build/native/main_05_transpose
```

| 指标 | 看什么 |
|---|---|
| `l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum` | v2（<32> 实例化）应有大量 bank conflict，v3（<33>）应接近 0 |
| `gpu__time_duration.sum` | 差 5.1%（29 µs） |
| `smsp__average_warps_issue_stalled_short_scoreboard` | 冲突态的 warp 停等应更长 |

**判据**：若冲突计数确实降下来了而时间只快 5%，就证实了"冲突真实存在、但被
共享内存的带宽余量吸收掉了"这个解释。

### v4/v5 为什么白干

| 指标 | 看什么 |
|---|---|
| `smsp__inst_executed.sum` | v4 应明显低于 v3（float4 让访存指令数降 4 倍） |
| `gpu__time_duration.sum` | 却几乎相同 → **省指令不等于省时间** |
| `dram__bytes.sum` | v5 与 v4 应完全一致（瓦片宽度不改变搬运量） |

### 各变体的静态资源（`python scripts/resource_report.py --chapter 05_transpose`）

| kernel | 寄存器 | smem | spill |
|---|---|---|---|
| `transpose_v0_kernel` / `v1_kernel` | 8 | 0 | 0 |
| `transpose_tiled_kernel<32>`（v2） | 24 | **4096 B** | 0 |
| `transpose_tiled_kernel<33>`（v3） | 24 | **4224 B** | 0 |
| `transpose_vec_kernel<32,33>`（v4） | 18 | 4224 B | 0 |
| `transpose_vec_kernel<64,65>`（v5） | 25 | **8320 B** | 0 |

**全部零 spill。** 注意 v2/v3 的共享内存正好差 **128 B**（4096 → 4224）——
那就是"一行 +1"的代价，也是这一章唯一那 5.1% 的来源。

## 6. CUDA → Ascend C 对照

| 概念 | CUDA（本章的写法） | Ascend C | 能不能平移 |
|---|---|---|---|
| 数据搬运 | 直接读写 global，靠硬件合并 | 显式 `DataCopy` GM↔UB，**手动管理** | ❌ 没有"自动合并"这回事 |
| **搬块** | 32×32 的 smem 瓦片 | 一次搬一块进 UB | ✅✅ **本章最该带走的一条**：转置的本质就是"分块搬 + 块内换位" |
| **对齐** | float4 要求 16 字节；行起点不齐就退回标量 | **32B 对齐**，长度要够整块 | ⚠️⚠️ **本章踩的坑在 Ascend 上更狠**：那边没有"自动退回标量"这回事，不对齐直接算错 |
| bank conflict | smem 的 32 个 bank（padding 消） | UB 的访问粒度/对齐 | ⚠️ 概念不直接对应，但"**访问模式决定有效带宽**"这条一样 |
| 读写不对称 | 跨步写要付 RMW（本章实测） | 搬出（写 GM）与搬入（读 GM）的代价也不同 | ⚠️ 结论要重新量，但**别默认读写对称** |
| 向量化 | float4（本章 v4，**没用**） | 天生向量指令 | ✅ 那边是默认行为，不是优化项 |

**给比赛的三条结论**：

1. **转置在 Ascend C 上是"分块搬运"的经典题**：`DataCopy` 一块进 UB →
   块内换位 → 搬出。本章 v1 → v2 那一级（1.28×）对应的就是"一定要经过片上内存"。
2. **对齐在 Ascend 上没有兜底**。本章的 float4 对齐坑在 CUDA 上只是退回标量（慢），
   在 Ascend 上是**算错**或直接失败。32B 对齐与整块长度要从第一行代码就管住。
3. **"读写不对称"值得在 Ascend 上也量一遍**。本章证明教科书的直觉可以整个反过来 ——
   搬入搬出的代价结构在 Ascend 上又是另一套，别照抄结论。

## 7. 踩坑记录

| 现象 | 真相 |
|---|---|
| 10 个测试用例全报 `CUDA error: misaligned address`，**连没有 float4 的 v0 也"失败"** | 一次 misaligned 访问会**污染 CUDA 上下文**，之后所有 API 调用都报同一个错 → 看起来像全盘崩溃，实际只有一个根因。排查时先找**第一个**报错的位置，别被后面的连坐误导 |
| float4 快路径在 `(31,33)` 上错位 | 只判了"尾部不足 4 个"，漏了"**行起点本身不对齐**"：`in_row*cols` 只有在 `cols%4==0` 时才对齐。修法：把对齐也算进快路径条件，host 侧算好传进 kernel |
| 部分瓦片上读出没写过的 smem 格子 | 转置的写回阶段下标是**交叉**的（输出行=输入列），所以两个边界条件也必须交叉。写成同向的话，在 M/N 不是 32 倍数的形状上会读到垃圾 |
| `x.t()` 当输入时结果"又转回去了" | `x.t()` 是**视图**。绑定层不先 `.contiguous()` 就取 `data_ptr()`，等于把"逻辑上的转置"当成"内存里的转置" |
| 以为跨步读比跨步写更惨 | **实测反了 1.81 倍**。跨步写的代价是"多搬字节"（部分 sector 写触发 RMW），跨步读只是"多发请求"（被 L2 接住） —— 前者伤带宽，后者伤事务率 |
| 以为 padding 消冲突能值 2~4 倍 | 实测 **5.1%**。共享内存比显存快 29 倍，即使被 32 路冲突打回原形也还剩 1.8 倍余量 —— **经典优化的量级必须按这台机器的带宽比重新算** |
| `git add kernels/05_transpose` 之后提交里没有内核 | 提交前**必须核对文件清单**：`git show --stat HEAD`。少提交内核 = 提交从全新 checkout 编译不过（这次真的发生了，靠 `--amend` 补回） |
