# 04 Scan（前缀和）

> 这一章的结论**和第 3 章正好相反**，而且是被自己的实测打脸打出来的：
>
> 第 3 章证明"块内优化测不出来"（因为归约的块内 work 是每元素 O(1)）；
> 这一章证明**同样的手法在 scan 上第一次能值 300~400 µs** ——
> 因为 scan 的块内 work 是每元素 **O(log B) 甚至 O(B)**。
>
> 还有一个反教科书的发现：**work-efficient 的 Blelloch 实测比 Kogge-Stone 慢 27%。**

---

## 1. 问题定义

| 算子 | 数学定义 | 输入 → 输出 | 理想 `bytes` | `flops`（名义） |
|---|---|---|---|---|
| `inclusive_scan` | `y[i] = Σ_{j≤i} x[j]` | `float32[N]` → `float32[N]` | 8N（读 4N + 写 4N） | N − 1 |

约束：`float32`；任意 `N ≥ 0`；输出与输入同形状；参考实现在 `float64` 上
（`x.reshape(-1).cumsum(0).reshape(x.shape)`）。

**两个和第 2、3 章不同的地方**：

1. **输出和输入一样大**，所以它和第 2 章的 elementwise 一样是"读一遍写一遍"的
   访存形态 —— 和第 3 章那种纯读完全不同。
2. **元素之间有前缀依赖**，而且依赖是**有序的**：算第 `i` 个输出要知道前 `i` 个。
   归约只需要"全加起来"（顺序无关），scan 不行。这是本章所有麻烦的根源。

> **多维输入按展平处理**（kernel 只认 numel 和连续内存，与第 2、3 章一致）。
> 逐行扫描是另一类算子（softmax / norm），第 6、7 章才讲。
> 边界测试里显式钉住了这个语义。

## 2. 先算两笔账（★ 写代码之前）

N = 2²³，B = 256。先算两笔账，整章的设计都建立在这上面。

### 第一笔：块内 work —— 这里和第 3 章分道扬镳

一个 256 元素的 chunk 要做多少次 smem 访问：

| 块内算法 | 每元素 work | 每 chunk | 全部 32768 个 chunk | 折算时间（768 次/cycle × 2 GHz）|
|---|---|---|---|---|
| **朴素**（每元素往前加一遍） | O(B) | ~3.3e4 | 1.07e9 | **~0.71 ms** |
| **Kogge-Stone** | O(log B) | ~4.6e3 | 1.5e8 | ~0.10 ms |
| **Blelloch** | O(1) 摊销 | ~1.3e3 | 4.2e7 | ~0.028 ms |

第 3 章那块内树只占理论下限的 **0.1%**；这里的朴素扫描是内存时间的 **2.7 倍**。
差别只在一条：**reduction 每个元素只参与一次合并（O(1)），scan 要参与 log B 次甚至 B 次。**

### 第二笔：全局流量 —— 多 block 合并第一次要付真钱

多 block 的 scan 必须先知道"前面所有 chunk 的和"。三段式（scan-scan-add）得读两遍输入：

| 方案 | 全局流量 | 理论下限 |
|---|---|---|
| 三段式（块和 → 扫块和 → 回加） | **12N** = 100.7 MB | 393.2 µs |
| 单趟 decoupled look-back | **8N** = 67.1 MB | **262.1 µs** |

第 3 章的多 block 合并是 144 次原子操作，**免费**；scan 的合并多了 50% 的流量。

### 于是有两组可证伪的预测（后来被打了脸，照实记在 §3）

- **工作轴**：v0 的块内 work 会超过内存时间 → ~30% 理想下限；v1 降到 O(log B) → 应该回到内存受限（12N 的 ~90%）；v2 更省 work → 应该 ≈ v1。
- **流量轴**：v3 把 12N 换成 8N → 应该比 v1/v2 快 45%。
- **摊销轴**（加测了 v3 之后才意识到）：每 chunk 付 8~18 次 barrier，chunk 只有 256 个元素 → **每元素 0.03 次 barrier**，这项没有摊销。

### ★ 一个必须写在前面的方法学决定：`%峰值` 的分母

本章**各变体的实际搬运量不同**（12N vs 8N），所以元数据给每个变体声明了自己的
`bytes`（见 `registry.variant_bytes()`），表里因此多出一列"实际搬运"，
`%峰值` 按**各自的实际流量**算。

这么做的代价是：v1/v2 的 `%峰值` 看起来不低（54.2% / 42.6%，因为它们的分母大），
**光看百分比会以为它们优化得还行**。所以判据必须是**时间**：
v4 的 291.8 µs vs v1 的 729.5 µs，差 2.5 倍 —— 而两者的 `%峰值` 都在"它们的流量下"是合理的。

> **`%峰值` 高不等于快。** 一个把 12N 优化到 90% 的版本（393 µs），
> 仍然打不过一个把 8N 做到 85% 的版本（308 µs）。
> 这条前几章没机会出现（大家字节数一样），是 scan 独有的陷阱。

### 这张表把我的预测打了三次脸，而每一次都值钱

| 预测 | 实测 | |
|---|---|---|
| v0 ≈ 理想下限的 30% | 3.37× 理想下限 | ✅ 接近 |
| v1 ~90% / 400~440 µs | 54.2% / 729.5 µs | ❌ 差 1.7 倍 |
| v2 ≈ v1 | **比 v1 慢 27%** | ❌ 方向反了 |
| v3 ~95% / 275 µs | 1874.9 µs（第一版） | ❌ 差 6.8 倍 |
| v4 300~330 µs | 291.8 µs | ✅ 略好 |
| v5 ~5% / 5 ms | 0.8% / 31177 µs | ❌ 差 6 倍 |

**① v2 比 v1 慢 27% —— 这是本章最有价值的一条。**
（三次实测分别给出 26% / 32% / 27%：v1 自己的**轮间极差就有 103.4 µs / 14%**，
所以**方向可信、幅度只能给区间**——大约 25~32%。结论不依赖具体幅度。）
Blelloch 的总 work 比 Kogge-Stone 少约 3 倍（每元素 O(1) 摊销 vs O(log B)），
但**级数 16 对 8，而且逐级变窄（活跃线程越来越少）**。
实测说明：块内扫描**"深度 + 发散"比"总 work"更值钱**。
我上一轮只数了 smem 访问次数，把这两件事忽略了 —— **work 只是成本的一维。**

**② v1/v2 停在 54.2% / 42.6%，差的是"每元素 barrier"。**
v1 的 12N 流量按实测带宽（239 GB/s）只值 **423 µs**，实测 729.5 µs，差的 **~306 µs**
不在内存上：每个 chunk 要付树归约 8 次 + KS 16 次 `__syncthreads()`，
而 chunk 只有 256 个元素 —— **每元素 0.03 次 barrier**，完全没被摊销。

**③ v3 第一版差了 6.8 倍，原因不是算法而是两处实现缺件**（详见 §4 与 §7）：

- **回看写成了单线程**：只让 `thread 0` 逐个往前找。同一轮 144 个 block 处理的是
  相邻 chunk，回看距离最长 144 步 = 144 次全局往返。改成**整 warp 并行**回看之后：
  **1874.9 → 699.4 µs（2.7×）**。
- **chunk 总和拿错了**：两级扫描重构时，我把"本线程 K 个元素之和"当成了 chunk 总和
  发布出去。全 1 输入下 chunk 0 发布的是 1 而不是 256，于是**从第二个 chunk 开始全错**。
  边界测试一击命中（见 §7）。

**④ 摊销这件事值多少钱，可以直接量出来：**

| | 流量 | 实测 | 相对实测带宽下限（423 / 281 µs）的差 |
|---|---|---|---|
| v3（K=1） | 8N | 699.4 | **+418 µs**（块内开销 + 回看） |
| v4（K=8） | 8N | 291.8 | **+11 µs** |
| v1（K=1） | 12N | 729.5 | +306 µs（只有块内开销） |

**把 chunk 从 256 放大到 2048（每线程 8 个元素），值约 400 µs** ——
而 v3 与 v4 的代码差别**只有一个模板参数**。

### 横向对比：把它放进前几章的"访存形态"表

| 访存形态 | 最好成绩 | %峰值 |
|---|---|---|
| 纯写（第 1 章 `hello`） | 253.0 GB/s | 98.8% |
| 纯读（第 3 章归约） | 244.4 GB/s | 95.5% |
| 读写混合（第 2 章 `add`） | 239.2 GB/s | 93.4% |
| **读 + 写（本章 scan）** | **230.3 GB/s** | **89.9%** |

scan 落在"读写混合"这一档里，比 `add` 低 3.5 个百分点 ——

## 4. 每级实现要点

### `v0_naive` —— 反面教材

```cuda
// 线程 t 把自己前面 t 个元素加一遍（块内 O(B²)）
for (int j = 0; j < t; ++j) acc += smem[j];
```

教科书上的朴素 scan 是"每个输出把全数组前缀加一遍"（O(N²)），在本仓库的规模下要跑几十分钟，
根本没法测。这里的版本把它限制在 chunk 内，**是同一个错误的可测量版本**：work 爆炸的机理一样。

实测 882.3 µs = 理想下限的 3.37 倍。注意它只比 v1 慢 21% —— 因为 6 个 block 同驻一个 SM，
一个 block 在傻算 smem 的时候，别的 block 的访存还在走，**块内 work 有一部分被掩盖了**。
这也是为什么"work 爆炸"没有变成 10 倍。

### `v1_kogge_stone` / `v2_blelloch` —— 换块内算法（各只差一个模板参数）

```cuda
// v1：8 级，每级每个线程 1 次读 + 1 次写
for (int offset = 1; offset < B; offset <<= 1) {
  float prev = (t >= offset) ? smem[t - offset] : 0.0f;
  __syncthreads();            // 先读进寄存器，再同步，最后才写
  smem[t] += prev;
  __syncthreads();
}
```

**`__syncthreads()` 的位置是这个 kernel 最容易写错的地方**：必须"先读、再同步、最后写"。
反过来写的话，同一级里后面的线程会读到本轮已被覆盖的值 —— 而且只在特定时序下错。

Blelloch 的上下扫同理，另外它的下扫每级只需要一次屏障（同一级里各线程读写的下标不相交）。

**它们的实测差距（v2 慢 27%）是本章的核心发现**，见 §3。

### `v3_single_pass` —— 单趟 look-back，K = 1

结构上把 12N 降到 8N：每个 block 处理完自己的 chunk 后，把**总和**发布到全局内存，
再往前回看（look-back）累加已发布的和，直到遇到一个**已算好的 inclusive 前缀**就停，
拿到前缀 → 加上 → 写回。输入只读了一遍。

三个必须说清楚的设计点（都写在 `scan_config.cuh` / `scan_lookback.cuh` 里）：

1. **`aggregate` 与 `inclusive` 必须分开两个数组。** 共用一个位置时会出现这种竞态：
   读者读到"只有 aggregate"，去读那个位置时，写者已经把它覆盖成 inclusive 前缀 →
   读者按 aggregate 累加，把前面所有 chunk **重复算一遍**。
2. **发布顺序 + `__threadfence()`。** 先写数据、栅栏、再写状态；读取方先读状态、栅栏、再读数据。
3. **所有 block 必须同时驻留**，否则自旋等待会**挂死**（不是报错）。护栏在 launcher 里：
   grid 上限取 `default_grid_size()`（恰好等于可驻留容量），超了直接抛异常。
   **笔记本上显卡同时驱动桌面，挂死很难受 —— 这个护栏不是洁癖，是保命。**

### `v4_optimized` —— 与 v3 只差一个模板参数（本章的答案）

```cuda
// scan_v4_optimized.cu 的全部内容就是这一行与 v3 不同：
launch_single_pass<kOptimizedItemsPerThread>(...);   // 8，而 v3 是 1
```

那 8 倍的摊销是怎么实现的（`scan_chunked.cuh`）——**三级结构**：

```
① 合并载入 → smem（striped 读，blocked 带 padding 写）
② 每线程**串行**扫自己那 K 个连续元素（寄存器里，1 次加法/元素）
③ 256 个 thread total 做一次块级扫描 ← 策略在这里起作用
④ 加回 thread 级前缀，经 smem 转置回 striped，**合并写回**
```

**为什么必须转置**：合并载入要求 thread t 读 `x[base + k·B + t]`（striped），
而"每线程串行扫连续 K 个"要求 thread t 拥有 `x[base + t·K .. +K)`（blocked）——
两者不一致，必须在 smem 里转一次。写回时再转回来：不转的话写会变成跨步，
一个 warp 32 条 cache line，**直接掉回第 2 章 v0 的下场**。

**padding 的作用**：blocked 布局的行长取 `K+1` 而不是 `K`。读 `smem[t·(K+1) + k]` 时
各线程地址模 32 两两不同（`K+1 = 9` 与 32 互质）→ 无 bank conflict。用 `K` 会退化成 8 路冲突。

**为什么 K=8 而不是 16**：smem 需要 `kBlockSize*(K+1)+1` 个 float。
K=8 → 9.2 KB，每 SM 仍能放 6 个 block（100% occupancy）；K=16 → 17.4 KB，只能放 5 个（83%）。
**这是一个可以单独调的旋钮**，调它不需要动任何算法。

### `v5_single_block` —— 故意回退

```cuda
scan_single_block_kernel<<<1, kBlockSize, 0, stream>>>(...);   // grid = 1
```

一个 block 顺序走过所有 chunk（用寄存器里的 carry 串起来）。实测 **31177 µs / 0.8%**：
31 ms ÷ 32768 chunk ≈ 0.95 µs/chunk ≈ 18 次 barrier 的串行开销 —— 全部压在**一个 SM** 上。

和第 3 章的 v4_single_block（慢 16.3 倍）是同一个教训，这次是 107 倍：
**用不满机器是第一位的问题，其余都在它后面。**

## 6. CUDA → Ascend C 对照

| 概念 | CUDA（本章的写法） | Ascend C | 能不能平移 |
|---|---|---|---|
| 前缀和 | 块内扫描 + 跨 block 前缀 | 向量指令 + `BlockReduce` 类的原语 | ✅ 层次一样，但块内那棵树不用你写 |
| **跨核前缀** | decoupled look-back（自旋 + 栅栏） | 核间只能靠 GM + 同步标志 | ⚠️ 概念可以搬，但**代价结构完全不同**：Ascend 的核少，回看距离短，收益也小 |
| **每线程多元素** | K=8 的两级扫描（本章的最大收益） | **同一件事**：一次搬一块进 UB、向量指令批量算 | ✅✅ **最该带走的一条**：把 per-block 的固定开销摊到更多数据上 |
| 块内算法选型 | KS 比 Blelloch 快（级数/发散 > 总 work） | 向量指令的"级数"概念不适用，但**流水深度**同样比总计算量值钱 | ⚠️ 结论要换形式，思路保留 |
| 数据搬运 | 直接读写 global，靠硬件合并 | 显式 `DataCopy` GM↔UB，**手动管理** | ❌ 没有"自动合并"这回事 |
| 同步 | `__syncthreads` / `__threadfence` | `TQue` 的 Set/Wait Flag，事件驱动 | ❌ 屏障式 vs 流水线式 |

**给比赛的三条结论**：

1. **`v3 → v4` 那一课是最值钱的**：算法结构选对之后，真正拉开差距的是
   "把 per-block/per-chunk 的固定开销摊到更多数据上"（这里 400 µs，占 60%）。
   Ascend C 上完全对应 "一次搬一大块进 UB 再批量算"，而且**那边没有自动合并帮你兜底**
   —— 这一条在 Ascend 上的权重只会更高。
2. **"work-efficient" 不是无条件的好**。本章实测 Blelloch 比 KS 慢 27%。
   在 Ascend C 上判断"该用哪个算法"时，**先看流水深度和搬运次数，再数计算量**。
3. **多核前缀依赖在 Ascend 上要重新设计**。CUDA 的单趟 look-back 靠的是
   "所有 block 同时驻留 + 自旋"，Ascend 的几十个核虽然更好保证同时驻留，
   但 GM 往返延迟与同步原语的代价完全不同 —— **别照抄，要重算那笔账**。

## 7. 踩坑记录

| 现象 | 真相 |
|---|---|
| 全 1 输入下，从第二个 chunk 开始**全体偏移**（n=257 时下标 256 得到 2，应为 257） | 两级扫描重构时，我把"**本线程 K 个元素之和**"当成了 chunk 总和发布出去（`total = acc` 而不是策略的返回值）。全 1 输入下 chunk 0 发布的是 `x[0] = 1` 而不是 256。**随机输入配 1e-3 容差会被吃掉一部分，只有全 1 输入能一击命中** —— 这条测试就是为它设计的 |
| v3 第一版 1874.9 µs，比自己的内存下限慢 6.8 倍 | look-back 写成了**单线程**（只让 `thread 0` 逐个往前找）。同一轮 144 个 block 是相邻 chunk，回看距离最长 144 步 = 144 次全局往返。改成整 warp 并行（一次比 32 个 predecessor）后 **1874.9 → 699.4** |
| 自旋等待会把 GPU **挂死**（不是报错） | 只要有一个 block 永远不发布状态，前面的 block 就一直等。护栏：grid 上限 = 可同时驻留容量，超了抛异常。这是这个算法的**前提条件**，不是优化 |
| per-lane 自旋让 `__ballot_sync` 永远等不齐 | warp 内各 lane 各转各的循环会发散，后面的 ballot 就凑不齐 32 个 lane。必须**整 warp 一起重试**：各读各的 → ballot 看有没有没就绪的 → 有就整体重来 |
| `aggregate` 与 `inclusive` 共用一个位置会**重复累加** | 读者读到"只有 aggregate"，再去读值时写者已把它覆盖成 inclusive 前缀 → 前面所有 chunk 被算两遍。这类 bug 只在特定时序出现，所以宁可多一个数组 |
| `%峰值` 看起来不低，时间却差 2.4 倍 | 各变体流量不同（12N vs 8N）。**用同一个分母算 %峰值就是拿两把尺子量东西** —— 所以元数据支持逐变体 `bytes`，表里另给"实际搬运"一列。判据必须是时间 |
| `%峰值` 高不等于快 | 12N 做到 90% 是 393 µs，8N 做到 85% 是 308 µs。**先看流量，再看百分比** |
| 写回如果不转置，会掉回第 2 章 v0 的下场 | blocked 布局直接写全局 = 一个 warp 32 条 cache line。必须经 smem 转回 striped 再合并写 |
| blocked 布局用 `K` 当行长会有 8 路 bank conflict | 行长取 `K+1`（与 32 互质）就能消掉；这是"padding 消 bank conflict"在 scan 上的第二次出现（第 3 章的 v2 是第一次） |

更细的方法学记录在 `docs/DESIGN.md` 的 M2 台账里。
